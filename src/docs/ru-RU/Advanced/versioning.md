# Версионирование и релизы

CubicLauncher использует **простую последовательную** схему:

- **Major** — целое число, увеличивающееся с каждым выпуском (27, 28, 29…).
- **Patch** — ревизии или хотфиксы в рамках одного major.

Внутри используется semver (`MAJOR.MINOR.PATCH`), потому что этого требует обновление Tauri. `MINOR` всегда равен `0`.

| Пользовательское обозначение | Внутренний semver |
| --- | --- |
| `27` | `27.0.0` |
| `27 rev 1` | `27.0.1` |
| `27 rev 2` | `27.0.2` |
| `28` | `28.0.0` |

Если `PATCH` равен `0`, отображается только major. Если он больше `0`, он показывается как `major rev patch`.

## Каналы обновлений

- **Стабильный** — рекомендуется большинству пользователей. Получает только опубликованные выпуски.
- **Предварительный** — alpha, beta и rc; может содержать нестабильные изменения.

Канал выбирается в разделе **Настройки → Лаунчер → Обновления**.

## Версионирование предварительных выпусков

Суффикс предварительной версии должен совпадать в `package.json`, `src-tauri/Cargo.toml` и `src-tauri/tauri.conf.json`, включая заголовок окна. Например, бета-версия `36.0.0-beta.1` должна быть указана так во всех трёх файлах. Если в `tauri.conf.json` указано `36.0.0`, обновление воспринимает её как финальную версию и отклоняет последующие беты того же major.

CI и релизные сборки проверяют это совпадение. Сборки по тегу также проверяют, что тег состоит из `v` и упакованной версии.

## Процесс публикации

Публикация проходит в два этапа, чтобы не распространять непроверенные бинарные файлы.

### 1. Создание тега

Перед созданием тега:

1. Синхронизируйте версию в `package.json`, `src-tauri/Cargo.toml` и `src-tauri/tauri.conf.json` (включая заголовок окна).
2. Обновите корневой `Cargo.lock` и проверьте из корня:
   ```bash
   cargo update --workspace --offline
   cargo clippy --workspace --locked -- -D warnings
   ```
   Если в локальном кеше отсутствуют зависимости, запустите первую команду без `--offline`. Включите обновлённый lockfile в тот же коммит, что и изменение версии.
3. Запустите проверку метаданных:
   ```bash
   bun test --conditions=browser ./tests/frontend/ui/versionMetadata.test.mjs
   ```
4. Создайте и отправьте тег:
   ```bash
   git tag v36.0.1
   git push origin v36.0.1
   ```

Для предварительных выпусков:

```bash
git tag v36.0.1-beta.1
git push origin v36.0.1-beta.1
```

### 2. Ожидание черновика

После отправки тега workflow `Build Release Draft` (или `Build Prerelease Draft`) собирает сборки для Linux, Windows и macOS и загружает бинарные файлы в GitHub **Release Draft** с автоматически созданными примечаниями. Выпуск пока **не является публичным**.

### 3. Проверка и публикация

Когда черновик готов, вручную запустите workflow `Publish Release` из GitHub Actions с указанием тега. Только после этого выпуск становится публичным, и обновление Tauri начинает его распространять.

Предварительные выпуски проходят тот же процесс, но помечаются как pre-release. Push в `develop` создаёт артефакты CI, не создавая публичный выпуск или новую версию.
